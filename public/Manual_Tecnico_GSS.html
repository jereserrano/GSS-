Capítulo 1. Introducción, Justificación y Alcance

1.1 Propósito del Documento

El presente Manual Técnico describe de forma exhaustiva la arquitectura de software, el modelo de datos, los protocolos de seguridad, la lógica de servidor y los procedimientos de instalación y despliegue del sistema GSS (Sistema de Información para el Seguimiento del Proceso de Integración con la Media Técnica). Este documento está dirigido a desarrolladores de software, arquitectos de sistemas, administradores de bases de datos (DBA), y personal de soporte de tecnologías de la información (TI) del Servicio Nacional de Aprendizaje (SENA).

1.2 Justificación del Proyecto

El programa de articulación con la Media Técnica del SENA involucra la coordinación de múltiples actores (instituciones educativas, sedes, instructores, aprendices, coordinadores y subdirectores) distribuidos geográficamente en la Regional Magdalena. Antes de la implementación de GSS, los procesos de control de asistencia, entrega de evidencias de aprendizaje, evaluación de resultados y seguimiento de riesgos de deserción se gestionaban de forma manual mediante hojas de cálculo, formularios físicos y comunicaciones por correo electrónico. Esta dispersión de datos generaba demoras en la consolidación de informes, pérdida de trazabilidad en las evaluaciones, imposibilidad de emitir alertas tempranas de deserción en tiempo real, y dificultades para cumplir con los requerimientos de auditoría del SENA.

GSS centraliza todos estos procesos en una plataforma web única, segura y accesible desde cualquier dispositivo con conexión a internet, eliminando la duplicidad de información, garantizando la trazabilidad de cada acción mediante un registro de auditoría inmutable (AuditLog), y habilitando notificaciones en tiempo real entre actores del proceso formativo.

1.3 Alcance Técnico

El alcance del sistema comprende los siguientes subsistemas funcionales: (a) Gestión Institucional (instituciones, sedes, programas y fichas), (b) Gestión de Actores (aprendices, instructores y docentes), (c) Estructura Académica (competencias, resultados de aprendizaje y plan de formación), (d) Ejecución Formativa (actividades, entregas de evidencias, asistencia y evaluaciones), (e) Seguimiento y Riesgos (alertas tempranas y visitas de seguimiento), (f) Administración del Sistema (usuarios, roles, auditoría, configuración y notificaciones), y (g) Reportes y Exportación de Datos.

Capítulo 2. Arquitectura del Sistema

2.1 Justificación del Monolito Modular con Next.js 15 App Router

La arquitectura adoptada es un Monolito Modular Moderno implementado sobre Next.js 15 con App Router. Esta decisión se fundamenta en tres criterios técnicos principales. Primero, la cohesión operativa: al mantener frontend y backend en una sola base de código, se elimina la complejidad de mantener servicios separados (API REST + SPA), se reduce la latencia de comunicación entre capas y se simplifica el despliegue a un único artefacto de producción. Segundo, la seguridad inherente: las Server Actions de Next.js ejecutan la lógica de negocio exclusivamente en el servidor, lo que impide que el código de acceso a la base de datos o las claves de conexión sean expuestas al cliente. Tercero, el rendimiento percibido: al utilizar React Server Components (RSC), el renderizado de componentes pesados (tablas con cientos de registros, gráficos analíticos) se realiza en el servidor antes de enviar el HTML al navegador, reduciendo drásticamente el JavaScript transferido al cliente.

2.2 Flujo de Interacción

El flujo de datos del sistema sigue un patrón unidireccional y seguro con cinco capas bien definidas:

  1. Capa de Presentación (Cliente): El navegador del usuario renderiza los componentes React. Los componentes de interfaz (botones, formularios, tablas) capturan las interacciones del usuario.
  2. Capa de React Server Components (RSC): Cuando una página requiere datos, los RSC ejecutan consultas directamente en el servidor antes de enviar el HTML resultante al cliente. Esto se implementa en los archivos page.tsx de cada ruta, que son funciones async que invocan acciones del servidor o consultan Prisma directamente.
  3. Capa de Server Actions: Las mutaciones (crear, actualizar, eliminar datos) se canalizan a través de Server Actions definidas en la carpeta /actions. Cada acción implementa: verificación de sesión (NextAuth.js), validación de permisos (RBAC jerárquico), validación de datos de entrada, interacción con la base de datos (Prisma), registro de auditoría (AuditLog), y revalidación de caché (revalidatePath).
  4. Capa de Persistencia (Prisma ORM): Las consultas y mutaciones a la base de datos se realizan mediante el cliente tipado de Prisma, que genera automáticamente las interfaces TypeScript a partir del esquema schema.prisma. Esto garantiza que cualquier error de tipo (campo inexistente, tipo incorrecto) sea detectado en tiempo de compilación.
  5. Capa de Almacenamiento (MySQL): La base de datos MySQL almacena todos los datos persistentes del sistema. Las tablas se mapean 1:1 con los modelos de Prisma mediante la directiva @@map.

Capítulo 3. Seguridad y Control de Acceso (RBAC)

3.1 Autenticación (NextAuth.js + bcrypt)

La autenticación del sistema se implementa mediante NextAuth.js configurado con la estrategia CredentialsProvider. El flujo de autenticación opera de la siguiente manera: (1) El usuario envía su correo electrónico y contraseña desde el formulario de inicio de sesión. (2) El servidor busca al usuario en la base de datos por su correo electrónico y verifica que su estado sea "ACTIVO". (3) La contraseña ingresada se compara contra el hash almacenado en el campo passwordHash utilizando bcrypt.compare() con un factor de coste de 10 salt rounds. (4) Si la verificación es exitosa, NextAuth.js genera un JSON Web Token (JWT) que contiene el ID del usuario, su nombre, correo, rol normalizado (por ejemplo, "INSTRUCTOR"), el nombre original del rol y su nivel jerárquico numérico. (5) Este JWT se almacena en una cookie HTTP-only segura y se propaga automáticamente en cada solicitud subsiguiente.

El callback jwt de NextAuth.js se encarga de poblar el token durante el primer inicio de sesión y de mantenerlo actualizado en sesiones posteriores. El callback session copia los datos del JWT (origen confiable del servidor) hacia el objeto session.user disponible en el cliente, incluyendo los campos role, rolName, hierarchyLevel e id. Crucialmente, el callback de actualización (trigger === "update") solo permite modificar campos no sensibles como el nombre, prohibiendo explícitamente la alteración del rol o nivel jerárquico desde el cliente.

3.2 Middleware Perimetral

El archivo middleware.ts en la raíz del proyecto actúa como primera línea de defensa. Utiliza withAuth de NextAuth.js para interceptar todas las solicitudes a las 24 rutas protegidas del dashboard antes de que lleguen a los componentes de página. El middleware ejecuta dos verificaciones secuenciales: primero, confirma que la solicitud contenga un JWT válido (verificación de autenticación); segundo, invoca la función canAccessRoute(role, pathname) del módulo de permisos para comprobar que el rol del usuario esté autorizado para acceder a la ruta solicitada (verificación de autorización). Si la autorización falla, el middleware redirige al usuario a la ruta /dashboard?denied=true en lugar de mostrar un error genérico.

Las rutas protegidas por el middleware se definen explícitamente en el array config.matcher, que incluye las 24 rutas del dashboard con el patrón /:path* para cubrir subrutas dinámicas (por ejemplo, /aprendices/[id] o /instituciones/[id]). Las rutas públicas como /login y /api/auth quedan fuera del matcher y son accesibles sin autenticación.

3.4 Defensa en Profundidad y Mitigación OWASP

Además del middleware perimetral, cada Server Action implementa una segunda capa de seguridad. Al inicio de cada mutación, se invoca getCurrentUserCtx() para extraer la sesión activa del JWT y verificar que el usuario siga autenticado en el momento exacto de la ejecución. Posteriormente, se valida la jerarquía del rol mediante la función canManageUser(), que compara el nivel jerárquico del solicitante contra el del usuario objetivo, impidiendo la escalación de privilegios (por ejemplo, un coordinador no puede modificar la cuenta de un administrador). Las entradas de usuario se validan mediante esquemas de Zod antes de interactuar con Prisma, mitigando ataques de inyección. React escapa automáticamente todo texto renderizado en el DOM, previniendo ataques XSS. Las contraseñas nunca se transmiten en texto plano ni se almacenan sin hashear.

Capítulo 5. Lógica de Servidor y Server Actions

5.1 Patrón de Implementación

Todas las Server Actions del sistema siguen un patrón arquitectónico uniforme con seis fases secuenciales: (1) Verificación de sesión mediante getServerSession(authOptions), que extrae el JWT y confirma que el usuario esté autenticado activamente. (2) Normalización del rol del usuario (se convierte a mayúsculas y se mapea a uno de los seis roles canónicos del sistema). (3) Verificación de autorización (RBAC) mediante funciones jerárquicas que comparan el nivel del solicitante contra los requisitos de la acción. (4) Validación de los datos de entrada. (5) Ejecución de la operación de base de datos mediante Prisma. (6) Registro de auditoría en el AuditLog y revalidación de caché con revalidatePath().

5.2 Especificación de Acciones Clave

evaluarEntregaAction (entregas.actions.ts)

Esta acción permite al instructor calificar una evidencia entregada por un aprendiz. Recibe como parámetros el ID de la entrega, el estado de evaluación (APROBADA, NO_APROBADA o CALIFICADA), la calificación numérica y la retroalimentación textual. Internamente actualiza los campos estado, calificacion, retroalimentacion y fechaEvaluacion de la tabla entregas. Tras la actualización exitosa, invoca crearNotificacionSistema() para enviar una notificación automática al aprendiz con el resultado de la evaluación, incluyendo un enlace a la ruta /actividades para que el aprendiz pueda consultar el estado directamente al hacer clic en la notificación. Finalmente, ejecuta revalidatePath('/entregas') y revalidatePath('/actividades').

guardarAsistenciaMasiva (asistencia.actions.ts)

Esta acción recibe un objeto con el ID de la ficha, el ID del instructor, la fecha de sesión y un array de detalles (uno por cada aprendiz con su estado: PRESENTE, FALLA o EXCUSA y observaciones). Internamente crea un registro padre en la tabla asistencias y múltiples registros hijos en detalles_asistencia dentro de una transacción de Prisma, calculando automáticamente los contadores totalPresentes, totalFaltas y totalExcusas.

createUser (user.actions.ts)

Esta acción crea una cuenta de usuario y automáticamente genera el perfil asociado según el rol. Tras crear el registro en la tabla users, evalúa el nombre del rol asignado: si contiene "APRENDIZ", crea un registro en la tabla aprendices vinculado al usuario; si contiene "INSTRUCTOR", crea un registro en la tabla instructores. Esto garantiza que todo usuario con rol operativo tenga su expediente funcional desde el momento de la creación de su cuenta.

Capítulo 6. Componentes de Frontend

6.1 Sistema de Componentes

La interfaz se construye con componentes organizados en tres niveles de abstracción. El primer nivel (/components/ui) contiene las primitivas de interfaz basadas en Radix UI y estilizadas con Tailwind CSS: Button, Input, Dialog, Select, Badge, Tooltip. El segundo nivel (/components/shared) contiene componentes reutilizables de negocio como DataTable (tabla genérica con paginación y búsqueda) y modales genéricos. El tercer nivel (/features) contiene los componentes específicos de cada dominio funcional agrupados por subdirectorio.

6.2 Componente Sidebar (Navegación por Roles)

El componente Sidebar.tsx define cinco arrays de navegación diferentes (navAprendiz, navInstructor, navCoordinador, navSubdirector, navAdmin), cada uno con las secciones y módulos específicos autorizados para ese rol. Al renderizarse, el componente lee el rol del JWT del usuario activo mediante useSession(), selecciona el array correspondiente y aplica un segundo filtro mediante canAccessRoute() para eliminar cualquier elemento que no esté autorizado según la whitelist de permisos. Esto implementa una defensa en profundidad visual, donde el usuario nunca ve opciones de menú para las que no tiene acceso.

6.3 Sistema de Notificaciones en Tiempo Real

El componente Header.tsx implementa un mecanismo de polling que consulta las notificaciones no leídas del usuario cada 30 segundos mediante getMisNotificacionesAction(). El contador de notificaciones se muestra como una insignia roja sobre el icono de campana. Al hacer clic en una notificación, se invoca marcarComoLeidaAction() y, si la notificación contiene un campo enlace, se navega automáticamente a la ruta correspondiente mediante router.push(enlace).

El archivo .env o .env.local en la raíz del proyecto debe contener las siguientes variables obligatorias:

NEXTAUTH_SECRET="clave_secreta_aleatoria_de_minimo_32_caracteres"

NEXTAUTH_URL="http://localhost:3000"

7.3 Procedimiento de Instalación

  1. Clonar el repositorio del proyecto: git clone [URL_DEL_REPOSITORIO] GSS
  2. Ingresar al directorio del proyecto: cd GSS
  3. Instalar las dependencias de Node.js: npm install
  4. Configurar las variables de entorno en el archivo .env.local según la sección 7.2.
  5. Ejecutar las migraciones de Prisma para crear el esquema en MySQL: npx prisma migrate deploy
  6. Generar el cliente tipado de Prisma: npx prisma generate
  7. (Opcional) Poblar la base de datos con datos iniciales (seed): npx prisma db seed
  8. Compilar la aplicación para producción: npm run build
  9. Iniciar el servidor de producción: npm start
  10. Verificar el acceso en el navegador: http://localhost:3000

7.4 Políticas de Backup y Mantenimiento

Se recomienda implementar las siguientes políticas de mantenimiento para entornos de producción: (a) Backup diario de la base de datos MySQL mediante mysqldump --single-transaction --routines --triggers nombre_bd > backup_$(date +%Y%m%d).sql, automatizado mediante cron a las 02:00 AM. (b) Retención de backups de al menos 30 días en almacenamiento externo (NAS o nube). (c) Migración del directorio /public/uploads a almacenamiento en la nube (AWS S3, Google Cloud Storage o Azure Blob) para evitar pérdida de archivos en redespliegues. (d) Actualización periódica de dependencias de seguridad mediante npm audit fix. (e) Monitoreo de logs del servidor y del registro de auditoría (AuditLog) para detectar anomalías.
